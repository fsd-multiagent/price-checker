# Adversarial review: spine update AD-26, AD-27 and `protected_paths` (2026-11-18)

Reviewer: adversarial (read-only on the spine). Scope: only the additions in the working-tree diff of `ARCHITECTURE-SPINE.md` (the `protected_paths` setting row, AD-26, AD-27, the AD-22 pointer), attacked against AD-4, AD-5, AD-6, AD-11, AD-12, AD-13, AD-15, AD-16, AD-20, AD-21, AD-23, AD-24 and ADR 0004 / ADR 0021. Code read for grounding: `orchestrator/src/sdlc/app/loop.py` (`_pre_commit_guards`, `_restore_gate_commands`), `core/scheduler.py` (`decide`), `core/epics_parser.py`, `core/sprint_status.py`, `adapters/gh.py` (`ensure_pr`), `sdlc/pipeline.yaml`, `.claude/hooks/guard.py`, `.github/workflows/*.yml`, `.github/CODEOWNERS`, `_bmad-output/planning-artifacts/epics.md`, ADR 0021.

## Verdict

**Not ready to bind.** The intent is sound (capture instead of discard; one review path for factory changes), but as written the update (1) makes every planned story and the infra stage that must change `.github/workflows/**` impossible to finish, (2) turns a reverted agent edit into a pushed branch that GitHub executes with an Azure OIDC token before any review, (3) lets a factory story switch off the guard for its own later steps and then self-merge, and (4) leaves the "blocked on owner review" state undefined against the AD-11 exit rule, so a run either exits and forgets the PR or holds the lock for days. Seven holes below; four are blocking.

## Two units that obey every AD and still break

**Scenario A: infra stage + story 1-x (CI workflow).** `epics.md` lists `.github/workflows/ci.yml`, `terraform-plan.yml`, `deploy.yml`, `kill-switch.yml`, `health-check.yml` in story `touches` (lines 340, 688, 715, 767, 791, 840). Pacala (DevOps) writes them in a normal story scope. AD-26 step 1 captures and reverts them (they match `.github/**`), so the committed branch lacks the workflow. AD-27 says a non-factory diff still touching a protected path fails its round, so the agent cannot even keep a partial edit. The `tests`/`review_verdicts` gates then fail on the missing AC (no workflow), rounds burn, the story escalates (AD-11, AD-14), and every dependent story is `blocked` (AD-14). Meanwhile each round's attempt opens another `proposal/<run-id>/<seq>` PR with the same workflow (dedupe is per `seq`, not per content). Every rule was obeyed; the run cannot deliver epic 3.

**Scenario B: factory story 0-42 + the queue.** The owner runs `sdlc story 42` (factory). Build passes, integrate opens the PR, labels `owner-review`, and the unit goes `blocked` ("waiting on owner review of PR #n"). Nothing else is running. Per the current `decide()`, a blocked unit with a non-null reason adds no action, so `Finish(exit_code=2)` fires at once: the lock is released, the issue gets no outcome comment (AD-27 "Finishing" only fires on merge/escalate), learn never runs, and nothing ever polls the PR again unless the owner remembers `sdlc resume`. If instead the implementer honours "the check repeats every tick" literally, the run is neither runnable, running nor waiting under AD-11, so the only way to keep ticking is to invent an unbounded wait: the lock is then held for days and every queued `sdlc story|fix|run` starves behind it. Both readings comply with the text; they diverge completely.

## Holes

### H1 (critical): `.github/**` as a proposal path blocks planned work in normal scopes

- **Where:** `protected_paths` default; AD-26 "On a normal branch (any scope of a run, except factory stories)"; AD-27 "non-factory story whose diff still touches a protected path ... fails its round".
- **Conflict:** AD-15 / `epics.md` stories and the infra stage (stage 6, Pacala (DevOps), `.claude/agents/devops-release.md` "Writes ... GitHub Actions workflows") must create workflows. AD-26 silently reverts them; AD-27 fails the round if any survive. Same for Aglaia (Knowledge Keeper), whose job includes `CLAUDE.md` (protected and bookkeeping): every learn step becomes a proposal, which is the "owner chore" AD-26 claims to prevent.
- **Fix rule:** split the list. `protected_paths` (owner review, never written by a normal scope): `sdlc/**`, `orchestrator/**`, `.claude/**`, `.github/CODEOWNERS`, the `sdlc-commands` block. `review_paths` (allowed in normal scopes, but a PR touching them gets `owner-review`, no auto-merge, and the unit takes the AD-27 owner-review path): `.github/workflows/**`, `CLAUDE.md`. A story whose `touches` intersects `protected_paths` is a load-time error unless it is a factory story, so the conflict is caught at parse, not after three rounds.

### H2 (critical): AD-26 pushes agent-written workflow code, which GitHub runs with an Azure OIDC token before review

- **Where:** AD-26 step 2 ("cuts `proposal/<run-id>/<seq>` ..., pushes, and opens a PR"); AD-27 factory story PRs.
- **Mechanism:** `.github/workflows/terraform-plan.yml` runs on `pull_request` with `id-token: write` and authenticates to Azure via OIDC (I-5). A same-repo branch's PR runs the workflow **from the PR head**. Before AD-26, a prompt-injected agent's workflow edit was reverted and never left the runner (ADR 0021 accepted only the auto-merge gap). AD-26 now materialises it as a pushed branch with an open PR, so the edited workflow executes on GitHub with the federated identity, e.g. `terraform apply`/`destroy` or reading the state blob, before the owner looks. This bypasses G1 ("a human runs apply") without touching the guard. Factory stories have the same exposure.
- **Fix rule:** a proposal or factory diff that touches `.github/workflows/**` is never pushed to `origin`; it becomes an `owner-review` issue carrying the patch text (AD-26 step 3 path), and the owner opens the PR. Independently, record in the owner checklist (plan §6) that the Azure federated credential subject must be `environment:<name>` with required reviewers, never `pull_request`, and that `terraform-plan.yml` gets an `environment:`.

### H3 (critical): a factory story can switch off the guard for its own later steps and then self-merge

- **Where:** AD-27 "protected paths are neither reverted nor turned into proposals"; AD-8 (`cwd` = worktree); AD-16 (later steps share the worktree).
- **Mechanism:** `claude -p` loads project settings and hooks from `cwd`. A factory story's dev step edits `<worktree>/.claude/settings.json` (drops the `PreToolUse` hook, widens `permissions.allow`) or `.claude/hooks/guard.py` (Edit/Write to these is allowed by G5; only Bash writes are blocked). The edit is committed, not reverted. Every later step in that worktree (QA, the parallel reviewers, the judge, the fix rounds) starts without G1–G5. The runner holds the owner's `gh` token, so an agent can run `gh pr merge --admin <own PR>` (G2 is gone; the adapter's "never `--admin`" binds only the orchestrator), push `main`, approve a retailer, or reach a non-approved domain. The `tests` gate also executes the story's modified `orchestrator/` code and `conftest.py` on the runner. The trigger is an issue body (H5), so this is reachable by text, not code.
- **Fix rule:** (a) `.claude/settings*.json`, `.claude/hooks/**` and `docs/source-register.md` are owner-only like G5: not proposal paths and not editable by factory stories (revert + fail round). (b) Every agent process runs with the guard settings of the **main checkout's `origin/main` tree**, e.g. `--settings <main-checkout>/.claude/settings.json` plus the hook path pinned to the main checkout, never the worktree's. (c) Before the integrate step, the orchestrator checks the PR is still open and unmerged by anyone but the owner; a PR merged by the runner's token without an owner approval review escalates the run.

### H4 (high): "blocked on owner review" has no defined lifetime against AD-11, the lock and the queue

- **Where:** AD-27 Owner-review integration ("the check repeats every tick") vs AD-11 exit rule vs AD-27 lock ("for the whole of a run").
- **Divergence:** see Scenario B. AD-5 `blocked` is "waiting on a human input ... consumes no round", but AD-11 counts only `resume_at` and budget waits as *waiting*. Also: `ci_green` and the rebase happen before the block, so after days of review the PR head is stale; the spine does not say whether the orchestrator rebases a blocked PR (AD-15 one fix round) or leaves it to the owner.
- **Fix rule:** add an explicit exit: a run whose only non-`DONE` units are `blocked` on owner review **finishes** with exit 2 and releases the lock; the state records `awaiting: [{scope, pr}]`. Every later `sdlc` invocation (any command, including the queue drain) first scans `runs/*/state.json` for `awaiting` PRs and, for one now `MERGED` or `CLOSED`, enqueues `sdlc resume <run-id>` ahead of new work. The orchestrator never rebases a PR under owner review; a conflict there is the owner's.

### H5 (high): the issue is untrusted input with no provenance check; the `factory` label is the whole authorisation

- **Where:** AD-27 "An issue labelled `factory` makes a factory story"; issue body parsed into `stories.yaml` and prompts.
- **Mechanism:** On the public repo, anyone with triage rights can add `factory`; the issue author can edit the body **after** the owner labels or runs it, and the body is read when the queued command runs, not when it was queued. `title` and `acceptance` strings flow into the build prompts, so the body is a prompt-injection channel that, with H3, reaches full runner compromise. Non-factory issue stories still auto-merge with 0 approvals, so an outsider-authored body becomes app code merged after CI.
- **Fix rule:** at `sdlc story|fix <issue>` (not at dequeue) record the body's SHA-256, the label set and the issue timeline. Refuse (escalate) unless the `factory` label and the last body edit were made by the owner login(s) listed in a new `settings.owners`, and the body hash at run start equals the recorded one. Render issue text into prompts only inside a fenced, quoted "untrusted data" section, and store it in `stories.yaml` as data.

### H6 (high): epic-0 keys collide with branches, PRs and `sprint-status.yaml`

- **Where:** AD-27 "the key is `0-<issue>-<slug>`" vs the block's own required `key` field; AD-12 branch names; AD-13 PR keyed by head branch; AD-21 `render_sprint_status`.
- **Mechanisms:**
  - The block carries `key` (schema of `epics.md`). The spine does not say the orchestrator derives or validates it. A block with `key: 3-2-deploy` passes `STORY_KEY`; its branch `story/3-2-deploy` is force-pushed with lease over a still-open PR of an escalated full run, and `ensure_pr` (open PRs by head) **reuses that PR**, so the new change lands under the old story's title and may auto-merge.
  - `sdlc story 42` then `sdlc fix 42` (or a re-run after escalation) reuse `story/0-42-slug` and `learn/0-42-slug`.
  - `depends_on` can only name stories in the same single-block file, so any dependency on an `epics.md` story is a parse error ("depends_on unknown story").
  - The learn stage's `render_sprint_status` renders only the run's own stories, so the learn PR of every issue run **replaces** `sprint-status.yaml` with just `epic-0` and drops epics 1..N (rendered by the last full run).
- **Fix rule:** in issue mode the orchestrator sets `key = 0-<issue>-<slugify(title)>` itself and rejects a block whose `key` is present and differs; `epics.md` rejects epic 0. Branch names include the run id for issue runs (`story/0-<issue>-<slug>/<run-id>` or a suffix) so reruns never share a ref. `depends_on` from an issue resolves against `epics.md` on `origin/main` and means "merged on main". `render_sprint_status` merges into the `origin/main` file (update the run's keys, keep the rest) instead of replacing it.

### H7 (medium): proposal capture, dedupe, resume and the lock are under-specified

- **Proposal state lives in an event.** `ProposalCaptured` is an event; AD-4 forbids deciding from `events.jsonl`. The proposal branch/PR is created "after the step's commit" outside a `script` step (AD-12 requires script steps with SHAs), so a crash between push and PR has no state to resume from. `ensure_pr` filters `--state open`, so after the owner merges or closes a proposal, a resume re-pushes and re-opens it (a rejected proposal comes back; a merged one fails to apply and becomes a duplicate issue). **Fix:** a `Proposal{scope, seq, patch_sha256, status, pr|issue}` record in `state.json`, created by a `propose` script step; look up by a body marker `<!-- sdlc-proposal:<patch_sha256> -->` with `--state all`; a closed or merged match is never recreated.
- **Dedupe is per `seq`.** The same edit re-made in each round (the AD-6 fix prompt names the discarded patch, which contains the protected edits) or by parallel stories yields one PR per attempt. **Fix:** key by normalised patch hash, as above.
- **Story-scope AGENTS.md.** Stories revert the whole `AGENTS.md` (AD-21). "The diff of the protected paths" for the block must be cut to the block's hunks; a whole-file diff leaks bookkeeping edits into the owner PR, and a factory story's "revert bookkeeping except the protected block" needs a new partial restore that is not specified. **Fix:** name both primitives (`extract_block_patch`, `restore_except_block`) and test them.
- **Factory change to the gate block** is tested only with the old `origin/main` commands; a broken new command fails every later story after merge. **Fix:** a factory story that changes the block must pass both the `origin/main` block and its own block (ADR 0004 is narrowed, not waived).
- **Lock.** pid-only staleness breaks on pid reuse after a reboot (lock never taken over, queue grows forever); "check lock, write queue" races with "queue empty, release" (orphaned queue entry). Draining the queue "in the same process" runs queued work on the pre-merge code and pipeline even after a factory PR merged, while gates read `AGENTS.md` from fresh `origin/main` (mixed versions). **Fix:** `fcntl.flock` on the lock file held for the process lifetime (the kernel frees it on crash), lock record `{pid, start_time, host, run_id}` for display only; queue append and the release decision both under the flock; after a run that merged a protected-path PR, the process stops draining and exits with a "main checkout is behind `origin/main`; pull and restart" message. Queued runs have no aggregate budget; add `settings.queue_budget_usd` or require the owner to start each queued run when triggers arrive (deferred work).

## Lower-severity notes

- `protected_paths` omits what also decides how agents behave: `_bmad/custom/*.toml` (BMAD agent overrides), `docs/standards/**` (the rules gates cite), `scripts/apply-persona-names.py`, `.gitignore` (AD-9 relies on `.sdlc/` being ignored). Add them, or record why not.
- `CLAUDE.md` matches only the root file; nested `*/CLAUDE.md` read by agents are unprotected. Use `**/CLAUDE.md` if intended.
- A merged proposal that changes `sdlc/pipeline.yaml` changes the stage-table digest (AD-7), so the very fix the owner merged can block `sdlc resume` of the escalated run. State which proposal-induced digest changes resume accepts.
- `proposal/<run-id>/<seq>` is missing from the AD-12 name list and from the Consistency Conventions table.
- A factory story whose diff ends up touching no protected path (only `pyproject.toml`, `docs/standards/`) auto-merges as a normal story. Either always route factory PRs through owner review, or say that is intended.
