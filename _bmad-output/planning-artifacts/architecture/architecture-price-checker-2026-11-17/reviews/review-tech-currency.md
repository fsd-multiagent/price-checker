## Findings (ordered by severity)

1. **Spring Boot "3.5.x or newer" is a poor floor. [HIGH]** From my knowledge, Spring Boot 3.5 open-source support ends around 2026-06-30, so by Nov 2026 it is out of OSS support (only paid commercial support remains). Spring Boot 4.0 (Spring Framework 7, Jackson 3, Java 17 to 25) went GA in Nov 2025, and a 4.1 line was due around mid-2026. Recommend: name the line explicitly as the latest GA Spring Boot 4.x with OSS support on the scaffold date, and forbid 3.5. The "3.5.x or newer" wording lets a scaffold pick an unsupported line. Unverified: check https://spring.io/projects/spring-boot#support for exact dates.
2. **Spring Boot 4 knock-on effects are not assessed. [MEDIUM]** Moving to 4.x changes things the spine relies on: Jackson 3 (package `tools.jackson`), modularised starters, and the Gradle floor (8.14+ or 9.x). The OpenAPI Generator `spring` output must target Boot 4 / Jackson 3 (check the `useSpringBoot3` or newer options in generator 7.x vs 8.x). The spine should require an early spike (generate, compile, run one test) and record the result in ADR 0007.
3. **Gradle "8.x or newer" is vague. [MEDIUM]** Gradle 9.x (9.0 in mid-2025) is the current major in my knowledge; 8.x is fine only if the chosen Boot line supports it. Recommend: Gradle 9.x via wrapper, pinned in `gradle-wrapper.properties` with a distribution SHA-256. The `-p backend` usage works (`--project-dir`), but the wrapper must live where the command finds it: the gate command is `backend/gradlew -p backend ...` (or one root wrapper). The AGENTS.md `sdlc-commands` rules forbid `cd`, so the spine/ADR 0014 must state the wrapper location.
4. **Node.js "22 LTS or newer LTS" should name 24. [LOW-MEDIUM]** In my knowledge Node 24 became Active LTS in Oct 2025 and Node 22 is in Maintenance LTS until about Apr 2027. Node 22 is not EOL in Nov 2026 but starts the project on a line with about 5 months left in the demo window. Recommend Node 24 LTS (CI `actions/setup-node`, web Dockerfile build stage). Unverified: https://nodejs.org/en/about/previous-releases.
5. **TypeScript "5.x" may be stale. [LOW-MEDIUM]** TypeScript 6.0 (the last JS-based line, bridge to the native 7.0 port) was expected in H1 2026. A "5.x" pin may block newer Vite/Vitest/ESLint typescript-eslint combinations. Recommend: latest stable at scaffold, remove the "5.x" cap. Unverified.
6. **Vite / Vitest / Playwright / ESLint "latest at scaffold" is fine, but pin compatibility. [LOW]** Vite 7 was current in my knowledge (Vite 8 possible by now), Vitest 3/4 tracks Vite, Playwright 1.5x. Risk is only mismatched majors (Vitest must support the chosen Vite; `@vitejs/plugin-react` must support the chosen Vite). The scaffold story should run the full web gate before committing the lockfile.
7. **Caffeine async single-flight claim is correct. [OK, unverified version]** `AsyncCache.get(key, (k, executor) -> CompletableFuture)` coalesces concurrent misses per key (Caffeine 3.x; latest I know is 3.2.x; Caffeine 2.x/3.x are Java 11+/Java 11+, so Java 21 is fine). Caveats the spine should note: (a) a failed future is evicted, so negative caching of failures does not happen (consistent with AD-10, only FOUND and NOT_FOUND cached, but the loader must return those, not throw, or the cache loads again on each call); (b) AD-11 wants the load on a virtual thread with a per-retailer deadline, so the cache must be given a virtual-thread executor and the deadline applied with `orTimeout` on the future, not inside the loader; (c) AD-10 checks Block and DISABLED before the cache, so the loader must not be invoked for them.
8. **jsoup 1.x: fits. [OK, unverified version]** Still the standard Java HTML parser; 1.2x line in my knowledge (1.21/1.22). No EOL concern. Pin the current patch; jsoup has had security fixes (e.g. XSS-cleaner and parser DoS advisories), so the lockfile/dependency scan (NFR-7) should cover it.
9. **crawler-commons 1.x: fits, with a policy gap. [OK, unverified version]** The library exists and has a `SimpleRobotRulesParser` that returns allow/deny per URL for a user agent, handles crawl-delay, and a size limit. Latest I know of is 1.5/1.6. Gap: AD-6 says robots.txt is cached 24 h and fetched by the fetch client; the parser does not fetch. Make explicit that a 4xx robots response means allow-all, a 5xx or timeout means deny-all (the library's `parseContent` takes the HTTP status path through `SimpleRobotRulesParser`/`BaseRobotsParser`; confirm the semantics against RFC 9309 at scaffold). Also the user-agent token matching: the fixed UA (AD-6) must contain a stable product token for robots matching, and that token must be what crawler-commons is given.
10. **ArchUnit 1.x: fits. [OK, unverified version]** The 1.4.x line was current in my knowledge and supports Java 21+ class files (needs 1.2+ for Java 21, 1.4.x for Java 24/25 bytecode). Caveat: if Boot 4 compiles to a newer bytecode than the ArchUnit version can read, tests fail with a class-file error, so pin ArchUnit to a version at least as new as the JDK used. Also: the rule "no class outside `fetch` imports `java.net.http`" is expressible; "contains a retailer domain, URL or CSS selector" (AD-1) is NOT expressible in ArchUnit (it inspects bytecode dependencies, not string constants); it needs a separate text-scan test. Fix the AD-1 wording or add that test.
11. **OpenAPI Generator "7.x" may be one major behind. [MEDIUM]** 7.x was current (7.1x) in my knowledge; an 8.0 line may have shipped by Nov 2026. Both the Gradle plugin (`org.openapi.generator`, generator name `spring`) and CLI `typescript-fetch` exist and work. The spine mixes "Gradle plugin" for Java and "CLI" for TypeScript: say how the CLI is run in CI and locally (npm `@openapitools/openapi-generator-cli` needs Java and downloads the jar; pin the version in `openapitools.json`) and that both use the same generator version. Known pain: `spring` generator defaults (interfaceOnly, useSpringBoot3, useJakartaEe, delegatePattern) must be set, and RFC 9457 problem+json is not generated natively (needs a hand-written error model reference).
12. **React 19.x, TypeScript, Testing Library, axe-core: fit. [OK, unverified]** React 19 (19.2 in my knowledge) is the current major. No issue with "no router, no state library".
13. **Caddy 2.x automatic HTTPS on `<label>.<region>.cloudapp.azure.com`: works in principle. [OK, unverified]** Azure public IP DNS labels give `<label>.<region>.cloudapp.azure.com`, and Caddy can obtain Let's Encrypt certificates for it via HTTP-01/TLS-ALPN-01 if ports 80 and 443 are open in the NSG (I-3 must allow 80, not only 443; the topology diagram only shows 443). Risks: (a) Let's Encrypt rate limits are per registered domain unless the suffix is on the Public Suffix List; I believe `cloudapp.azure.com` is on the PSL (unverified), which would give per-label limits; if not, shared limits could block issuance; (b) the Caddy data volume (`/data`) must be persisted in Compose, otherwise each redeploy re-issues certificates and can hit rate limits; (c) the Caddyfile access log must be off to meet AD-14 (Caddy's default is no access log, but the `log` directive must not be added). The spine says the DNS name is deferred to Pacala; the constraint "Caddy can get a certificate for it" is correct and should be verified in the first deploy.
14. **GHCR: fits. [OK, unverified]** Package visibility defaults to private for first push; the VM needs a read token (PAT or `GITHUB_TOKEN` is not usable on the VM) or the images must be set public. The spine does not say which. Decide in ADR 0015 (simplest for the demo: public images, since they contain no secrets, and AD-8 bakes only public register content).
15. **Terraform "1.x" + azurerm "4.x": fits. [OK, unverified]** azurerm 4.x requires `subscription_id` to be set explicitly in the provider block (breaking change from 3.x). A Terraform 1.x line (1.13/1.14 in my knowledge) is fine; pin `required_version` and the provider with `~>` and commit `.terraform.lock.hcl`. Consider that HashiCorp licensing is BUSL since 1.6; OpenTofu is not needed for a demo, but note it in ADR 0015 if the project prefers OSS licences.
16. **Java 21 (Temurin) [ADOPTED]: fits, one note. [OK, unverified]** Java 21 is an LTS with Temurin support well past 2026, and virtual threads (AD-11) are GA in 21. Java 25 LTS (Sep 2025) is now available and supported by Boot 4.x. Staying on 21 is fine; mention that choice is deliberate, not drift. Virtual-thread pinning in Java 21 on `synchronized` blocks (fixed in 24+) can affect libraries that hold monitors during I/O; with the JDK HTTP client this is not a problem.
17. **Docker Compose / Spotless / google-java-format / Testing Library / axe-core: no concern. [unverified]** google-java-format needs `--add-exports` flags on JDK 21 through Spotless; Spotless handles it, verify on the scaffold build.

## Process recommendation

The spine's "verify at scaffold" deferral is acceptable for patch versions, but not for the **Spring Boot line**, the **Gradle major**, the **Node LTS** and the **OpenAPI Generator major**, because these shape the architecture (Jackson 3, generator output, bytecode level for ArchUnit). Either research those four before the spine is accepted, or add an explicit "stack spike" as story 1 with a pass/fail check (generate, compile, one test, one Playwright run) and an ADR recording the pinned versions with source URLs.
